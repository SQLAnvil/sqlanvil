# Testing

## Levels

| Level | Harness command | Environment | Gate |
|---|---|---|---|
| unit | `scripts/bazel-ci test //... --test_tag_filters=-integration --build_tests_only` | local | build |
| integration | `scripts/bazel-ci test //tests/prd/... --test_tag_filters=integration --build_tests_only --test_output=all` | local | build |
| warehouse | `scripts/bazel-ci test //tests/integration/... //tests/api/... //tests/release/... //cli/... --test_tag_filters=integration --build_tests_only --test_env=HOME --test_env=PATH` | local | deploy |

- **Lifecycle.** Bazel builds the code under test and runs each test target. The Postgres and Supabase integration specs start their own Docker container (image `pgvector/pgvector:0.8.7-pg15`), one per spec on its own host port (5432 `postgres.spec`, 5433 `supabase.spec`, 5434 `supabase_rls.spec`); the MySQL fixture starts `mysql:8` on 3306 and MariaDB on 3307. When `PG_*`, `SUPABASE_*` or `MYSQL_HOST` variables are passed with `--test_env`, the fixture uses that database and skips Docker. The BigQuery spec uses a real GCP project through `test_credentials/bigquery.json`. A case that needs `@duckdb/node-api` to fail to load runs its code in a child Node process started with a `--require` preload whose module resolver throws for that package (owner, 2026-11-22): the child is `nodePath --require testing/resolver-patch.js --require <the blocking preload> <a child script>`, where `testing/resolver-patch.js` resolves `sa/...` imports the way the test runner does, and the preload and the child script live in the suite's own folder (owner, 2026-11-22). A CLI case runs the bundled CLI with Node, `execFile(nodePath, [cliEntryPointPath, ...argv])` (`cliEntryPointPath` from `sa/cli/index_test_base`, which is `packages/@sqlanvil/cli/bundle.js`; it and `nodePath` are absolute paths, made with `path.resolve`, so a child's `cwd` does not change them), inside `getProcessResult` from `sa/testing`, which gives the exit code, stdout and stderr (`nodePath` is exported by `sa/testing` and is Bazel's own Node; `getProcessResult(childProcess)` takes the ChildProcess that `execFile` returns and resolves `{exitCode, stdout, stderr}`, owner, 2026-11-22); its `ts_test_suite` lists `//packages/@sqlanvil/cli:bundle`, `//packages/@sqlanvil/cli:json` and `//packages/@sqlanvil/cli:worker_bundle` in `data`, as `cli/BUILD` does (owner, 2026-11-22).
- **Environment switch.** A case's `env:` reaches the code it calls this way: for a call in the test's own process, the test sets each variable on `process.env` for the call and restores the old value after it; for a CLI case, the variables are added to the child's environment (owner, 2026-11-22). The Bazel tag and the target path decide the level: targets tagged `integration` under `tests/prd/` run in the integration level (the characterization suites), targets tagged `integration` under `tests/integration/`, `tests/api/`, `tests/release/` and `cli/` in the warehouse level, which needs Docker and `test_credentials/bigquery.json` and so runs at the deploy gate, on the owner's machine, not in CI (E-012), and everything else in the unit level (owner, 2026-11-22). A database is chosen by the `PG_HOST`, `PG_PORT`, `PG_USER`, `PG_PASSWORD`, `PG_DATABASE` (or `SUPABASE_*`, `MYSQL_HOST`) variables passed with `--test_env`; with none, the fixture's own container on 127.0.0.1 is used. No test publishes to npm or reads the npm-beta or npm environments; the one npm call a test makes is FR-033's `:package.publish` with `--dry-run` against a local stub registry passed with `--registry`, under an empty npm user config (`--userconfig` an empty file under the case's temporary directory), so the owner's npm login is never read and nothing is uploaded (owner, 2026-11-25); the only remote system a test uses is the BigQuery test project `sqlanvil` behind `test_credentials/bigquery.json`, which is not production (owner, 2026-11-22).
- **Database access.** A test reads and writes a warehouse through sqlanvil's own adapters (`sa/cli/api/dbadapters`, for example `PostgresDbAdapter.create(...)`) and reads rows back with the helpers in `tests/integration/utils.ts`.
- **Tools on the runner.** Bazelisk, installed so that `bazel` is on PATH (on macOS, `brew install bazelisk` puts both in `/opt/homebrew/bin`), which runs Bazel 7.3.2 from `.bazelversion`, and Docker on PATH; a `~/.npmrc` file, empty if nothing else, because `MODULE.bazel` sets `use_home_npmrc = True` and rules_js fails when the file is missing. Every Bazel command in Levels and in the §5 standards rows runs through `scripts/bazel-ci`, which creates an empty `~/.npmrc` when there is none and then runs `bazel` with its own arguments, so a runner without one (such as the generated CI's) can build (E-008, owner, 2026-11-23); Bazel downloads Node.js 24.13.0 and pnpm 9.7.1 itself. Full-tree builds on macOS need `--config=macos-cpp`. The release script cases take `git` and `/bin/sh` from the system PATH (`/usr/bin`) (owner, 2026-11-26).
- **Clean state.** Each integration spec drops the test schemas it uses before it runs, so a spec starts from no leftover tables of its own. A characterization case that names `P` makes it a new empty directory with `fs.mkdtemp` under `os.tmpdir()` and removes it after the case (under Bazel `os.tmpdir()` is the system temporary directory, such as `/tmp`, not `TEST_TMPDIR`, so the removal is the test's own job). Any other directory a case names (Q, P2, D) is made and removed the same way; a character its name must hold, such as a single quote, goes in the `mkdtemp` prefix (for example `o'brien-`). A file a case creates without stated contents holds any bytes the test chooses (owner, 2026-11-22); the artifacts suite creates no warehouse schemas (owner, 2026-11-22). Which schemas a warehouse area's characterization suite may create: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22).
- **Persistent environments.** The BigQuery project behind `test_credentials/bigquery.json` keeps data between runs. How its fixtures get there and what a test must never do there: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22).
- **Layout.** Unit tests sit beside the code they test as `*_test.ts` in `core/`, `cli/`, `sqlx/`, `common/` and `testing/`, run by the unit level's command (those directories mix tests with code, so they are not test roots); warehouse specs are `tests/integration/*.spec.ts`, `tests/api/*.spec.ts` and the CLI's live-BigQuery end-to-end test `//cli:run_e2e_tests` (`cli/index_run_e2e_test.ts`), each a `ts_test_suite` target (from `//testing:index.bzl`) in the directory's `BUILD` file, tagged `integration`, with sample projects as `data`. The characterization suite lives under `tests/prd/`, one directory per area (`tests/prd/artifacts/` for the artifacts area), as `ts_test_suite` targets tagged `integration` (owner, 2026-11-22). A test cites its T-id at the start of its test name, `test("@prd T-001.1 <what it checks>", …)`, so each runner result names its T-id; a known-failing case's name starts `@prd <T-id> known-failing <E-nnn>` (owner, 2026-11-22). `sa/testing` has no expected-failure mode, so a known-failing case is written as a strict expected failure with a helper in the suite's own `tests/prd/` folder: it runs the case body and passes only when the body fails with the case's `symptom:`, and fails when the body passes or fails some other way; `sa/testing` itself is not changed (owner, 2026-11-22). Error text quoted in a `symptom:` is matched as a substring of the failure's message, and only the case's own symptom counts as the expected failure: any other failure, even one in a related file, fails the test (owner, 2026-11-22). A symptom that names a state, not error text, is seen when the test observes that state before its other assertions; only then does it raise the expected failure (owner, 2026-11-22). A characterization test calls the code under test through these modules (read from the code at @984785d8, owner, 2026-11-22): `queryParquet(sql: string, views: ArtifactView[])` and `writeParquet(rows: object[], outPath: string, columns: string[])` from `sa/cli/api/dbadapters/duckdb_artifacts`, where an `ArtifactView` is `{name: string, glob: string}` and a case's views are an array of them, one per view the case names (`actions`, `dependencies` and `columns` with globs `<P>/target/catalog/<name>.parquet`, `runs` with glob `<P>/target/runs/*.parquet`, `run_summary` with glob `<P>/target/run_summary/*.parquet`); `queryParquet` resolves to the rows as plain objects keyed by column name. `buildDocsModel(views: ArtifactView[], generatedAt: string)` and `renderDocsHtml` from `sa/cli/api/commands/docs`, `writeArtifacts` and `safeWriteArtifacts` from `sa/cli/api/commands/artifacts`, `run` and `evaluate` from `sa/cli/api/commands/query`. `writeParquet` creates the missing parent directories of `outPath`. A protobufjs Long value is `Long.fromNumber(n)`, with `Long` the default import of the `long` package (`import Long from "long"`, as the repository's own code imports it). The `sqlanvil` proto namespace is imported as `import { sqlanvil } from "sa/protos/ts"`; a case's graph and run result are passed as plain objects, with enum values from `sqlanvil.TableType`, `sqlanvil.RunResult.ExecutionStatus` and `sqlanvil.ActionResult.ExecutionStatus`, not built with `.create` (owner, 2026-11-22). The Bazel labels are `//cli/api` (the `sa/cli/api/...` modules), `//cli:index_test_base`, `//protos:ts`, `//testing`, `//:node_modules/@duckdb/node-api`, `//:node_modules/long`, `//:node_modules/chai`, `//:node_modules/@types/chai` and `//:node_modules/@types/node`. A suite's `ts_test_suite` sets `name`, `srcs`, `data`, `tags` and `deps`; of its `srcs`, the files named `*.spec.ts` or `*_test.ts` run as tests and the other `.ts` files are shared helpers (`testing/index.bzl`) (owner, 2026-11-22). `writeArtifacts(compiledGraph: sqlanvil.ICompiledGraph, projectDir: string, options?: {runResult?: sqlanvil.IRunResult, runId?: number})` resolves `{targetDir}`; `safeWriteArtifacts` takes the same parameters, its options adding `warn?: (message: string) => void`, and resolves nothing. Both accept plain objects of those interface shapes. A test may cast the model it passes to `buildDocsModel` or `renderDocsHtml` to `any` (owner, 2026-11-22). A stub database adapter for `query.run` or `query.evaluate` is a plain object holding only the methods its case names (`execute`, `evaluate`), cast to `any` where it is passed. In a stub's evaluations, `status: SUCCESS` and `FAILURE` name members of `sqlanvil.QueryEvaluation.QueryEvaluationStatus`, and the result is compared with the stub's own object, which `query.evaluate` returns unchanged (owner, 2026-11-22). Test roots: `tests/`, `testing/` The release area's cases (owner, 2026-11-25): its integration-level suite is a `ts_test_suite` under `tests/prd/release/` that takes the package tarballs (`//packages/@sqlanvil/cli:package_tar`, `//packages/@sqlanvil/core:package_tar`, `//packages/sample-extension:package_tar`) and the binaries it runs (`//packages:gen-package-json-bin`, `//packages/@sqlanvil/cli:bin`, `//packages/@sqlanvil/core:package.publish`) as Bazel `data`, and runs each binary from its runfiles, never through `bazel run`. A test reads a tarball's entries with a tar library, never with macOS `tar tzf`, which hides the `._*` entries npm publishes; any tar reader serves, one the suite writes itself over Node's `zlib` included, and no tar package or Bazel label is required (owner, 2026-11-26). A test finds a runfile at `<RUNFILES_DIR or TEST_SRCDIR>/_main/<path>`, and a `package_tar` output's path is its package path followed by `package.tar.gz`, as `packages/@sqlanvil/core/package.tar.gz`; a `js_binary` named `n` in package `p` is the runfile `p/n_/n`, as `packages/@sqlanvil/cli/bin_/bin` and `packages/gen-package-json-bin_/gen-package-json-bin`, and "the runfiles root" a case runs from is `<RUNFILES_DIR or TEST_SRCDIR>/_main` (owner, 2026-11-26). A path a case writes as `T/...` is the absolute path of that file under T (owner, 2026-11-26). A release_github case makes its repository R as a new git repository in its temporary directory, with a bare repository there as `origin`, and puts a stub `gh` first on PATH that records each call and answers as the case's `gh_stub` says; where the case is silent the stub answers as `contracts/dependencies/github.yaml`'s `expects` says, with `release view` exiting 1 (owner, 2026-11-26). A regenerate_docs case of FR-040 uses only the files its input names under T, a plain directory (not a git repository), with T as its working directory; an FR-041 case uses the clone `T/repo` (owner, 2026-11-26). Each named run under a case's `runs:` starts from its own fresh T and repository, unless the case says the runs share state (owner, 2026-11-26). A release_github run gets the test's own environment without `VERSION` and `DRY_RUN`, plus `WHATS_NEW` and the case's variables, with the gh stub first on PATH and git configuration kept from the owner's: `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL` an empty file under T (owner, 2026-11-26). R's `init` commit holds every file the case puts in R; a file a case gives as "exactly these lines" or as `lines: '…'` is written with a final newline; the script's PATH is the gh stub's directory followed by the test's own PATH; and `notes_file_lines_recorded_by_gh_stub` are the lines of the notes file the stub copied on the case's one `release create` or `release edit` call (owner, 2026-11-26). In a release case, `stdout_line` and `stderr_line` mean one line of that output equals the given text (owner, 2026-11-26). In a release case, `sorted_specifiers` is the sorted list of distinct specifiers, and `tag_line_starts` means exactly one stdout line starts with `Tag` and that line starts with the given text (owner, 2026-11-26). A script case's `errors:` names the contract entry its failure belongs to; where that entry's message is another command's own output, the test asserts only the output and effects the case lists (owner, 2026-11-26). A binary a release case runs gets the test's own environment plus the case's `env:`, as a CLI case does; `//packages:gen-package-json-bin` runs with T as its working directory, so `BAZEL_BINDIR: "."` is relative to T, `//packages/@sqlanvil/cli:bin` runs from the runfiles root and changes to `BUILD_WORKING_DIRECTORY` itself, and `:package.publish` runs as its case says (owner, 2026-11-26). The regenerate_docs success paths (FR-041), which need Docker and the network for typedoc's `npm install`, are a `ts_test_suite` tagged `integration` under `tests/release/`, in the warehouse level; no integration-level case uses Docker or the network. A release test reads the repository's own files (`LICENSE`, `NOTICE`, the READMEs, `protos/*.proto`, `package.json`, `.bzl`, bundler config and script files) from the workspace root, found by following the `//:version.bzl` runfile to its real path, and never adds an `exports_files` or other target outside the test roots to reach them (owner, 2026-11-26). A warehouse release case runs `scripts/regenerate_docs` with the HOME and PATH the warehouse command passes in with `--test_env`, so its `node`, `npm` and `docker` are the owner's own and npm uses the owner's cache (owner, 2026-11-26). The workspace root is the directory of the `//:version.bzl` runfile's real path; when that directory holds no `.git` (a sandboxed run), it is the directory of the real path of `<output base>/execroot/_main/version.bzl`, where the output base is the part of the runfile's path before `/execroot/` with any `/sandbox/…` part removed. The owner's checkout, whose root `node_modules` an FR-041 case links into its clone, is the path written in `<output base>/DO_NOT_BUILD_HERE`; Bazel's execroot has no `node_modules` (owner, 2026-11-26). FR-033's case runs the publish binary from the real Bazel output bin directory with `RUNFILES_DIR` set to the binary's `.runfiles` directory (and `RUNFILES_MANIFEST_FILE` when it holds a `MANIFEST`), and points npm's cache at `<T>/npm-cache` with `npm_config_cache`, since the test sandbox cannot write `~/.npm` (owner, 2026-11-26). A release case's compiled graph G is a `sqlanvil.ICompiledGraph`: its tables are `G.tables`, each with `target.name` and `query`, and its compilation errors are `G.graphErrors.compilationErrors`, each with `message` (owner, 2026-11-26). `sa/core` and `sa/core/session` come from the Bazel label `//core`, and a test loads `sa/core` before `sa/core/session` (owner, 2026-11-26). The sample extension's `bundle.js` is a CommonJS module that exports `extension` by name and needs no other module at run time, so a case's `T/ext` holds only the extracted package; `extension().compile(request, session)` is synchronous and returns nothing (owner, 2026-11-26). A webpack configuration is loaded in a child Node process started with `--require testing/resolver-patch.js`, its working directory the workspace root and `BAZEL_BINDIR` removed from its environment; the configuration's own `BAZEL_BINDIR` check runs before anything it needs from `node_modules` (owner, 2026-11-26). A case's `throws:` value is the error's whole message, compared for equality (owner, 2026-11-26). A script case (release_github, regenerate_docs) runs with the case's repository, R or `T/repo`, as its working directory unless the case names another (owner, 2026-11-26). In an FR-041 case the commit under test is the HEAD of the owner's checkout, and `T/repo` is a `git clone --shared` of that checkout at HEAD; the test takes `//protos:ts` and `//core:version` as `data` and copies `protos/ts.d.ts` and `core/version.ts` from its runfiles into `T/repo/bazel-bin/` (owner, 2026-11-26).
- **HTTP requests.** Not applicable: sqlanvil has no HTTP API; BigQuery is reached through its client library inside the adapter.
- **Fixtures.** A sample project is a directory under the test's own folder, exposed to the test by `:files` and `:node_modules` targets in its `BUILD` file and passed as `data`. How a case's `contracts/fixtures/` preconditions are loaded before the test body, and what Load paths are relative to: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22); no artifacts case has a precondition.
- **Browser identity.** Not applicable: sqlanvil has no browser UI.
- **Assertions.** Tests use `suite` and `test` from `sa/testing` and chai's `expect`. `suite(name, fn)` or `suite(name, options, fn)` defines a suite, and `fn` receives a context whose hooks include `beforeEach` and `afterEach`; `test(name, fn)` or `test(name, {timeout}, fn)` defines a test, and `fn` may be async (testing/suite.ts, testing/test.ts; owner, 2026-11-22). `sa/testing` runs top-level suites at the same time and a suite's tests one after another, so a spec file holds one top-level suite. A test shows what an in-process call wrote to stdout or stderr by replacing `process.stdout.write` and `process.stderr.write` with recorders for the call and restoring them after it (owner, 2026-11-22). Each `*.spec.ts` of a `ts_test_suite` runs as its own `js_test`, in its own process. The PRD names no pack, so no pack helper applies (owner, 2026-11-22). `query.run(dbadapter, query, options?: {compileConfig?, rowLimit?, byteLimit?})` returns a CancellablePromise of the rows; `renderDocsHtml(model)` returns the HTML as a string, not a Promise, and `buildDocsModel` resolves a Promise (owner, 2026-11-22). A count a case names ("the two execute calls", "called exactly once") is exact. A graph a case describes in prose (such as G21 in T-018.3) holds only what it names: every other action list is empty, and a table with no stated type has no `enumType` (owner, 2026-11-22). CLI stdout is split into lines as a file is (on `\n`, one final newline allowed, no CRLF), and a case's line numbers count from 1, so `stdout_lines_9_to_10` is the 9th and 10th lines (owner, 2026-11-22). An expected value of `"absent"` means the object has no such key at all, not a key that holds undefined or null (owner, 2026-11-22). Only the fields a case lists are asserted; fields it does not list are ignored. A list compares element by element, in the order the case gives. Generated text (SQL, HTML, CLI output) is matched as the case words it, contains or equals, and is never whitespace-normalised unless the case says so (owner, 2026-11-22).
- **Waits.** A characterization test waits at most the `sa/testing` default of 30 s (owner, 2026-11-22). A warehouse release case (FR-041) waits at most 30 minutes: its test passes `{timeout: 1800000}` to `test`, and its `ts_test_suite` sets `timeout = "eternal"` and the tags `integration`, `no-sandbox` and `requires-network` (owner, 2026-11-26). `ts_test_suite` (`testing/index.bzl`) takes an optional `timeout` and passes it to each of its tests, never to the library it builds (owner, 2026-11-26). How long an expectation waits for a container, a table or a warehouse run: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22).
- **Effects.** An effect on a file is checked as the case words it (exists, holds, is unchanged byte for byte). A directory "gains no new file or directory" when no file or directory appears anywhere beneath it, at any depth (owner, 2026-11-22). The files under a directory are "unchanged" when the same set of files is there, at every depth, each identical byte for byte, so a new file counts as a change (owner, 2026-11-22). A path is "still the same regular file" when it is still a regular file and its bytes are unchanged; its inode is not compared (owner, 2026-11-22). A file "holds the lines a and b" when its content, split on `\n` with one final newline allowed, is exactly those lines in that order, with no CRLF (owner, 2026-11-22). Which columns an effect on a warehouse table checks, and what "unchanged" compares there: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22).
- **Leaks.** A leak check scans the CLI's stdout and stderr for each credential value the case passes in `.df-credentials.json` (`password`, `accessToken`, a service-account `private_key`), as an exact substring. A failure report names the field that leaked, never its value (owner, 2026-11-22).
- **Acceptance.** Not applicable: sqlanvil is a CLI and library verified by its automated levels; no case needs a person's sign-off (owner, 2026-11-22).
