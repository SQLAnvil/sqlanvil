# Testing

## Levels

| Level | Harness command | Environment | Gate |
|---|---|---|---|
| unit | `scripts/bazel-ci test //... --test_tag_filters=-integration --build_tests_only` | local | build |
| integration | `scripts/bazel-ci test //tests/prd/... --test_tag_filters=integration --build_tests_only --test_output=all` | local | build |
| warehouse | `scripts/bazel-ci test //tests/integration/... //tests/api/... //cli/... --test_tag_filters=integration --build_tests_only` | local | deploy |

- **Lifecycle.** Bazel builds the code under test and runs each test target. The Postgres and Supabase integration specs start their own Docker container (image `pgvector/pgvector:0.8.7-pg15`), one per spec on its own host port (5432 `postgres.spec`, 5433 `supabase.spec`, 5434 `supabase_rls.spec`); the MySQL fixture starts `mysql:8` on 3306 and MariaDB on 3307. When `PG_*`, `SUPABASE_*` or `MYSQL_HOST` variables are passed with `--test_env`, the fixture uses that database and skips Docker. The BigQuery spec uses a real GCP project through `test_credentials/bigquery.json`. A case that needs `@duckdb/node-api` to fail to load runs its code in a child Node process started with a `--require` preload whose module resolver throws for that package (owner, 2026-11-22): the child is `nodePath --require testing/resolver-patch.js --require <the blocking preload> <a child script>`, where `testing/resolver-patch.js` resolves `sa/...` imports the way the test runner does, and the preload and the child script live in the suite's own folder (owner, 2026-11-22). A CLI case runs the bundled CLI with Node, `execFile(nodePath, [cliEntryPointPath, ...argv])` (`cliEntryPointPath` from `sa/cli/index_test_base`, which is `packages/@sqlanvil/cli/bundle.js`; it and `nodePath` are absolute paths, made with `path.resolve`, so a child's `cwd` does not change them), inside `getProcessResult` from `sa/testing`, which gives the exit code, stdout and stderr (`nodePath` is exported by `sa/testing` and is Bazel's own Node; `getProcessResult(childProcess)` takes the ChildProcess that `execFile` returns and resolves `{exitCode, stdout, stderr}`, owner, 2026-11-22); its `ts_test_suite` lists `//packages/@sqlanvil/cli:bundle`, `//packages/@sqlanvil/cli:json` and `//packages/@sqlanvil/cli:worker_bundle` in `data`, as `cli/BUILD` does (owner, 2026-11-22).
- **Environment switch.** A case's `env:` reaches the code it calls this way: for a call in the test's own process, the test sets each variable on `process.env` for the call and restores the old value after it; for a CLI case, the variables are added to the child's environment (owner, 2026-11-22). The Bazel tag and the target path decide the level: targets tagged `integration` under `tests/prd/` run in the integration level (the characterization suites), targets tagged `integration` under `tests/integration/`, `tests/api/` and `cli/` in the warehouse level, which needs Docker and `test_credentials/bigquery.json` and so runs at the deploy gate, on the owner's machine, not in CI (E-012), and everything else in the unit level (owner, 2026-11-22). A database is chosen by the `PG_HOST`, `PG_PORT`, `PG_USER`, `PG_PASSWORD`, `PG_DATABASE` (or `SUPABASE_*`, `MYSQL_HOST`) variables passed with `--test_env`; with none, the fixture's own container on 127.0.0.1 is used. No test publishes to npm or reads the npm-beta or npm environments; the only remote system a test uses is the BigQuery test project `sqlanvil` behind `test_credentials/bigquery.json`, which is not production (owner, 2026-11-22).
- **Database access.** A test reads and writes a warehouse through sqlanvil's own adapters (`sa/cli/api/dbadapters`, for example `PostgresDbAdapter.create(...)`) and reads rows back with the helpers in `tests/integration/utils.ts`.
- **Tools on the runner.** Bazelisk, installed so that `bazel` is on PATH (on macOS, `brew install bazelisk` puts both in `/opt/homebrew/bin`), which runs Bazel 7.3.2 from `.bazelversion`, and Docker on PATH; a `~/.npmrc` file, empty if nothing else, because `MODULE.bazel` sets `use_home_npmrc = True` and rules_js fails when the file is missing. Every Bazel command in Levels and in the §5 standards rows runs through `scripts/bazel-ci`, which creates an empty `~/.npmrc` when there is none and then runs `bazel` with its own arguments, so a runner without one (such as the generated CI's) can build (E-008, owner, 2026-11-23); Bazel downloads Node.js 24.13.0 and pnpm 9.7.1 itself. Full-tree builds on macOS need `--config=macos-cpp`.
- **Clean state.** Each integration spec drops the test schemas it uses before it runs, so a spec starts from no leftover tables of its own. A characterization case that names `P` makes it a new empty directory with `fs.mkdtemp` under `os.tmpdir()` and removes it after the case (under Bazel `os.tmpdir()` is the system temporary directory, such as `/tmp`, not `TEST_TMPDIR`, so the removal is the test's own job). Any other directory a case names (Q, P2, D) is made and removed the same way; a character its name must hold, such as a single quote, goes in the `mkdtemp` prefix (for example `o'brien-`). A file a case creates without stated contents holds any bytes the test chooses (owner, 2026-11-22); the artifacts suite creates no warehouse schemas (owner, 2026-11-22). Which schemas a warehouse area's characterization suite may create: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22).
- **Persistent environments.** The BigQuery project behind `test_credentials/bigquery.json` keeps data between runs. How its fixtures get there and what a test must never do there: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22).
- **Layout.** Unit tests sit beside the code they test as `*_test.ts` in `core/`, `cli/`, `sqlx/`, `common/` and `testing/`, run by the unit level's command (those directories mix tests with code, so they are not test roots); warehouse specs are `tests/integration/*.spec.ts`, `tests/api/*.spec.ts` and the CLI's live-BigQuery end-to-end test `//cli:run_e2e_tests` (`cli/index_run_e2e_test.ts`), each a `ts_test_suite` target (from `//testing:index.bzl`) in the directory's `BUILD` file, tagged `integration`, with sample projects as `data`. The characterization suite lives under `tests/prd/`, one directory per area (`tests/prd/artifacts/` for the artifacts area), as `ts_test_suite` targets tagged `integration` (owner, 2026-11-22). A test cites its T-id at the start of its test name, `test("@prd T-001.1 <what it checks>", …)`, so each runner result names its T-id; a known-failing case's name starts `@prd <T-id> known-failing <E-nnn>` (owner, 2026-11-22). `sa/testing` has no expected-failure mode, so a known-failing case is written as a strict expected failure with a helper in the suite's own `tests/prd/` folder: it runs the case body and passes only when the body fails with the case's `symptom:`, and fails when the body passes or fails some other way; `sa/testing` itself is not changed (owner, 2026-11-22). Error text quoted in a `symptom:` is matched as a substring of the failure's message, and only the case's own symptom counts as the expected failure: any other failure, even one in a related file, fails the test (owner, 2026-11-22). A symptom that names a state, not error text, is seen when the test observes that state before its other assertions; only then does it raise the expected failure (owner, 2026-11-22). A characterization test calls the code under test through these modules (read from the code at @984785d8, owner, 2026-11-22): `queryParquet(sql: string, views: ArtifactView[])` and `writeParquet(rows: object[], outPath: string, columns: string[])` from `sa/cli/api/dbadapters/duckdb_artifacts`, where an `ArtifactView` is `{name: string, glob: string}` and a case's views are an array of them, one per view the case names (`actions`, `dependencies` and `columns` with globs `<P>/target/catalog/<name>.parquet`, `runs` with glob `<P>/target/runs/*.parquet`); `queryParquet` resolves to the rows as plain objects keyed by column name. `buildDocsModel(views: ArtifactView[], generatedAt: string)` and `renderDocsHtml` from `sa/cli/api/commands/docs`, `writeArtifacts` and `safeWriteArtifacts` from `sa/cli/api/commands/artifacts`, `run` and `evaluate` from `sa/cli/api/commands/query`. `writeParquet` creates the missing parent directories of `outPath`. A protobufjs Long value is `Long.fromNumber(n)`, with `Long` the default import of the `long` package (`import Long from "long"`, as the repository's own code imports it). The `sqlanvil` proto namespace is imported as `import { sqlanvil } from "sa/protos/ts"`; a case's graph and run result are passed as plain objects, with enum values from `sqlanvil.TableType`, `sqlanvil.RunResult.ExecutionStatus` and `sqlanvil.ActionResult.ExecutionStatus`, not built with `.create` (owner, 2026-11-22). The Bazel labels are `//cli/api` (the `sa/cli/api/...` modules), `//cli:index_test_base`, `//protos:ts`, `//testing`, `//:node_modules/@duckdb/node-api`, `//:node_modules/long`, `//:node_modules/chai`, `//:node_modules/@types/chai` and `//:node_modules/@types/node`. A suite's `ts_test_suite` sets `name`, `srcs`, `data`, `tags` and `deps`; of its `srcs`, the files named `*.spec.ts` or `*_test.ts` run as tests and the other `.ts` files are shared helpers (`testing/index.bzl`) (owner, 2026-11-22). `writeArtifacts(compiledGraph: sqlanvil.ICompiledGraph, projectDir: string, options?: {runResult?: sqlanvil.IRunResult, runId?: number})` resolves `{targetDir}`; `safeWriteArtifacts` takes the same parameters, its options adding `warn?: (message: string) => void`, and resolves nothing. Both accept plain objects of those interface shapes. A test may cast the model it passes to `buildDocsModel` or `renderDocsHtml` to `any` (owner, 2026-11-22). A stub database adapter for `query.run` or `query.evaluate` is a plain object holding only the methods its case names (`execute`, `evaluate`), cast to `any` where it is passed. In a stub's evaluations, `status: SUCCESS` and `FAILURE` name members of `sqlanvil.QueryEvaluation.QueryEvaluationStatus`, and the result is compared with the stub's own object, which `query.evaluate` returns unchanged (owner, 2026-11-22). Test roots: `tests/`, `testing/`
- **HTTP requests.** Not applicable: sqlanvil has no HTTP API; BigQuery is reached through its client library inside the adapter.
- **Fixtures.** A sample project is a directory under the test's own folder, exposed to the test by `:files` and `:node_modules` targets in its `BUILD` file and passed as `data`. How a case's `contracts/fixtures/` preconditions are loaded before the test body, and what Load paths are relative to: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22); no artifacts case has a precondition.
- **Browser identity.** Not applicable: sqlanvil has no browser UI.
- **Assertions.** Tests use `suite` and `test` from `sa/testing` and chai's `expect`. `suite(name, fn)` or `suite(name, options, fn)` defines a suite, and `fn` receives a context whose hooks include `beforeEach` and `afterEach`; `test(name, fn)` or `test(name, {timeout}, fn)` defines a test, and `fn` may be async (testing/suite.ts, testing/test.ts; owner, 2026-11-22). `sa/testing` runs top-level suites at the same time and a suite's tests one after another, so a spec file holds one top-level suite. A test shows what an in-process call wrote to stdout or stderr by replacing `process.stdout.write` and `process.stderr.write` with recorders for the call and restoring them after it (owner, 2026-11-22). Each `*.spec.ts` of a `ts_test_suite` runs as its own `js_test`, in its own process. The PRD names no pack, so no pack helper applies (owner, 2026-11-22). `query.run(dbadapter, query, options?: {compileConfig?, rowLimit?, byteLimit?})` returns a CancellablePromise of the rows; `renderDocsHtml(model)` returns the HTML as a string, not a Promise, and `buildDocsModel` resolves a Promise (owner, 2026-11-22). A count a case names ("the two execute calls", "called exactly once") is exact. A graph a case describes in prose (such as G21 in T-018.3) holds only what it names: every other action list is empty, and a table with no stated type has no `enumType` (owner, 2026-11-22). CLI stdout is split into lines as a file is (on `\n`, one final newline allowed, no CRLF), and a case's line numbers count from 1, so `stdout_lines_9_to_10` is the 9th and 10th lines (owner, 2026-11-22). An expected value of `"absent"` means the object has no such key at all, not a key that holds undefined or null (owner, 2026-11-22). Only the fields a case lists are asserted; fields it does not list are ignored. A list compares element by element, in the order the case gives. Generated text (SQL, HTML, CLI output) is matched as the case words it, contains or equals, and is never whitespace-normalised unless the case says so (owner, 2026-11-22).
- **Waits.** A characterization test waits at most the `sa/testing` default of 30 s (owner, 2026-11-22). How long an expectation waits for a container, a table or a warehouse run: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22).
- **Effects.** An effect on a file is checked as the case words it (exists, holds, is unchanged byte for byte). A directory "gains no new file or directory" when no file or directory appears anywhere beneath it, at any depth (owner, 2026-11-22). The files under a directory are "unchanged" when the same set of files is there, at every depth, each identical byte for byte, so a new file counts as a change (owner, 2026-11-22). A path is "still the same regular file" when it is still a regular file and its bytes are unchanged; its inode is not compared (owner, 2026-11-22). A file "holds the lines a and b" when its content, split on `\n` with one final newline allowed, is exactly those lines in that order, with no CRLF (owner, 2026-11-22). Which columns an effect on a warehouse table checks, and what "unchanged" compares there: no adopted area uses it yet; the first warehouse area (postgres, bigquery or mysql) decides it with the owner before its suite is written (owner, 2026-11-22).
- **Leaks.** A leak check scans the CLI's stdout and stderr for each credential value the case passes in `.df-credentials.json` (`password`, `accessToken`, a service-account `private_key`), as an exact substring. A failure report names the field that leaked, never its value (owner, 2026-11-22).
- **Acceptance.** Not applicable: sqlanvil is a CLI and library verified by its automated levels; no case needs a person's sign-off (owner, 2026-11-22).
